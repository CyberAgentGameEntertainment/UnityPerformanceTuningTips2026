# Unity LTO Settings and Performance Comparison on Android and iOS

Name：Minhyuk Kim  
Affiliation：CyberAgent, Inc. SGE Core Technology Division

The link-time optimization (LTO) setting for Android added in Unity 6000.5 applies only to engine code. A separate setting is required to apply LTO to the code generated from your own C\#. We tried both settings and measured performance, binary size, and build time with benchmarks and real titles.

## 1\. IL2CPP Compilation and Translation Units

In a Unity Android build (IL2CPP), C\# is converted to machine code through the following flow: {{list:il2cpp_build_flow}}.  
CODE START text | IL2CPP build processing flow {{list:il2cpp_build_flow}}  
C\# Source  
  ↓ C\# Compile  
IL Assembly (.dll)  
  ↓ IL2CPP Convert  
A large amount of C++ (.cpp)          <- "IL2CPP generated code"  
  ↓ clang Compile with (each .cpp is optimized individually)  
  ↓ Link  
libil2cpp.so               ← C\# Final native binary generated from the code  
CODE END  
clang compiles C++ per translation unit (commonly called a TU) and produces object files. A TU is the unit that the compiler reads and optimizes individually.

In a normal C++ build, a function body in another TU cannot be referenced, so even short functions may not be inlined and a call instruction may remain. IL2CPP generated code contains many small functions and safety checks, so it is particularly affected by this constraint. For example, the single C\# line \`buf\[idx\]\` becomes roughly the following C++: {{list:il2cpp_bounds_check}}.
CODE START cpp | Example of array access code generated by IL2CPP {{list:il2cpp_bounds_check}}  
if (buf \== NULL) ThrowNullReferenceException();               // null check  
if ((uint32\_t)idx \>= buf-\>max\_length) ThrowIndexOutOfRange(); // bounds check  
val \= buf-\>m\_Items\[idx\];  
CODE END  
As the generated code grows, calls across TUs also increase, and so does the total time spent on calls.

## 2\. What Are LTO and ThinLTO

LTO (Link Time Optimization) is a clang/LLVM mechanism that performs inlining, constant propagation, and dead code elimination across TUs at link time. At compile time, object files are emitted as LLVM bitcode (an intermediate representation before optimization). At link time, they are optimized together and machine code is generated.

Full LTO merges all intermediate representations into one and optimizes them. It has the widest optimization scope, but because merging and optimizing the intermediate representations are concentrated in a single process, it uses a large amount of memory in large builds. In this case as well, memory usage reached 20 GB during the build of a real title, and the OS forcibly terminated the process.

ThinLTO creates a summary of each TU at compile time. At link time, it imports the required functions from other TUs and optimizes in parallel. It keeps memory usage and processing time lower than full LTO and is widely used in large builds.

## 5\. How to Apply LTO to \`libil2cpp.so\`

To apply LTO to \`libil2cpp.so\` that includes code converted from C\#, you can use Unity's Master configuration or pass clang flags directly.

### 5.1 Master Configuration and the IL2CPP LTO Mode Setting

![][image4]{scale=0.85}  
図: Settings screen for IL2CPP LTO Mode and C++ Compiler Configuration {{fig:il2cpp_player_configuration}}  
Setting C++ Compiler Configuration in Player Settings ▸ Configuration to Master enables LTO for \`libil2cpp.so\`. \`IL2CPP LTO Mode\` is the item that selects the Thin / Full mode used in that case.

According to Unity's official article, IL2CPP LTO Mode was added in 6000.5.
On Android before 6000.5, there is no difference between Release and Master regarding the presence of LTO.
However, in 6000.5 the toggle cannot be selected on the Android platform and is fixed to Thin; from 6000.6, Thin / Full can be selected in the Master configuration. Even as of 6000.7, there is no option that enables only LTO while keeping the Release configuration.

The flags corresponding to C++ Compiler Configuration in Player Settings can be checked in IL2CPP compiler configuration in the Bee build graph (Il2CppCompilerConfiguration).
表: Compiler flags by Unity C++ Compiler Configuration {{table:compiler_configuration_flags}}  
| Version | Release | Master |  
| \---------------------- | \------------ | \------------------- |  
| Android 6000.3 (arm64) | \-Os (size-oriented), no LTO | \-Os, no LTO (identical) |  
| Android 6000.5 (arm64) | \-Os | \-O2 (optimization balancing speed and code size) \+ ThinLTO |  
| iOS 6000.3 / 6000.5    | \-O3 (optimization that pursues speed more aggressively at the cost of possible code size growth), LTO OFF | \-O3, LTO OFF (identical)  |  

### 5.2 Adding \`-flto=thin\` to the Release Configuration

As described above, switching to the Master configuration is the fastest way to obtain the effect of LTO, but the optimization level also changes from \`-Os\` to \`-O2\` at the same time as LTO ({{table:compiler_configuration_flags}}), and the drawbacks are increased size and build time. If you keep the Release configuration and apply only ThinLTO, you can measure the effect of LTO separately and also limit the increase in size and build time. To apply ThinLTO to \`libil2cpp.so\` generated from your own C\#, you can pass clang flags directly, as in {{list:manual_thinlto_build}}.

CODE START csharp | Build preprocessing that enables ThinLTO in the Release configuration {{list:manual_thinlto_build}}  
// Save the existing additional arguments → append → always restore  
var saved \= PlayerSettings.GetAdditionalIl2CppArgs();  
try  
{  
    var extra \= "--compiler-flags=-flto=thin \--linker-flags=-flto=thin";  
    PlayerSettings.SetAdditionalIl2CppArgs(  
        string.IsNullOrEmpty(saved) ? extra : saved \+ " " \+ extra);  
    BuildPipeline.BuildPlayer(options);  
}  
finally  
{  
    PlayerSettings.SetAdditionalIl2CppArgs(saved);  
}  
CODE END  
Verify whether it has been applied in two steps ({{list:il2cpp_thinlto_verification}}).

The first is whether the flag was passed to the build commands. Unity's build system (Bee) records the compile and link commands it executed in \`Library/Bee/Player\*.dag.json\`. Search this file with \`-flto=thin\` and check that the flag is included in both the compilation of the IL2CPP-generated code and the link of \`libil2cpp.so\`.

The second is whether the generated object files are LLVM bitcode. When LTO is enabled, the compile output \`.o\` is bitcode instead of machine code. Select one output file of a compile command found in the first step and display its first 4 bytes.

CODE START bash | Commands to confirm IL2CPP ThinLTO is applied {{list:il2cpp_thinlto_verification}}  
\# 1\. Check whether the compile and link commands contain \-flto=thin  
rg \-n \-- '-flto=thin' Library/Bee/Player\*.dag.json  
\# 2\. First 4 bytes of the generated object (specify the .o found in 1\.)  
xxd \-l 4 Library/Bee/artifacts/Android/.../GeneratedCode.o  
CODE END  
For bitcode, \`4243 c0de\` (\`BC..\`) is displayed; for an ordinary machine-code object, \`7f45 4c46\` (\`.ELF\`) is displayed. If you pick an arbitrary \`.o\` in the folder, you may pick up an object of a third-party library that is not subject to LTO. For the second command, always specify a file that appeared in the search results of the first.

### 5.3 Benchmark Design

#### 5.3.1 Generating Synthetic Code

This benchmark mainly measures calls across TUs, which normal compilation cannot optimize.  
An asmdef boundary and a C++ TU boundary are not the same concept, so I checked the generated C++ after IL2CPP conversion and  
also confirmed in the Bee compile graph that the caller and callee fall into different TUs.  
The code generator produces the following.  
\- 16 asmdef assemblies × 24 classes × 8 methods \= 3,072 methods  
\- One round of the call chain passes through 16 assembly boundaries, and every method additionally calls helpers in a shared assembly (\`Core.Mix\` / \`Core.Idx\` / struct operations)  
\- The benchmark visits all classes, so managed stripping does not remove them  
\- A different constant per method prevents folding by ICF

{{pagebreak}}

An example of the 3,072 generated methods is shown in {{list:generated_method_example}}.
CODE START csharp | Example of a method generated by the synthetic benchmark {{list:generated_method_example}}  
public static int M2(int sel, int x, int\[\] buf)  
{  
    x \= Core.Mix(x, 655663086);      // Cross-boundary call to the shared assembly  
    x \+= buf\[Core.Idx(x, 7)\];        // Array access with bounds check (Idx is masked with & 1023)  
    return M3(sel, x, buf);          // Small function chain  
}  
CODE END

#### 5.3.2 Two Workloads

表: Synthetic benchmark workloads for IL2CPP ThinLTO {{table:il2cpp_workloads}}  
| Workload | What it measures |  
|---|---|  
| direct | Cross-assembly static call chain (the form where LTO should be most effective) |  
| iface | The same kind of operations run through interface dispatch (a form where LTO has difficulty resolving the callee directly) |  
Both are self-contained within \`libil2cpp.so\`. For the binary generated in each configuration,  
I verified the md5 of \`libil2cpp.so\` extracted from the APK every time.  
The iteration count is adjusted at run time so that one sample takes about 100ms. Because the count differs per run, values are normalized to the time per pass for comparison.

In iface, four classes implementing \`IGenOp\` are generated for each assembly (64 in total), and the benchmark calls them in turn through the interface ({{list:generated_iface_example}}). The method body calls the same \`Core.Mix\` / \`Core.Idx\` as direct, but which class's \`Apply\` is called is determined at runtime.

{{pagebreak}}

CODE START csharp | Classes and call loop generated for the iface workload {{list:generated_iface_example}}  
sealed class Op0 : IGenOp  
{  
    int m\_State \= 20612;  
    public int Apply(int x, int\[\] buf)  
    {  
        x \= Core.Mix(x, 347275849);             // Cross-boundary call to the shared assembly  
        x \+= buf\[Core.Idx(x ^ m\_State, 7)\];   // Array access of the same kind as direct  
        m\_State \= (m\_State \+ x) | 1;  
        return x;  
    }  
}  
  
// Benchmark side: iterate over the 64 implementations through the interface  
for (int i \= 0; i < ops.Count; i++)  
    a \+= ops\[i\].Apply(a ^ p, buf);       // The callee is determined at runtime  
CODE END

### 5.4 CPU Measurements (Pixel 8a)

表: CPU measurement results of IL2CPP ThinLTO on a Pixel 8a {{table:il2cpp_cpu_results}}  
| Configuration | direct (us/pass) | iface (us/pass) |  
|---|---|---|  
| off(Release, \-Os) | 19.88 | 0.404 |  
| thin (manual ThinLTO) | 15.54 (-21.8%) | 0.375 (-7.3%) |  
Manual ThinLTO reduced direct by 21.8% and iface by 7.3%.

#### Function calls and instruction counts in direct

For the same call structure as in §5.3.1, I compared the disassembly with and without LTO.
表: Disassembly comparison of the direct workload {{table:direct_disassembly}}  
| \`C000\_M2\` | No LTO | ThinLTO |  
|---|---:|---:|  
| Instruction count | 15 | 11 |  
| Function calls (\`bl\`) | 2 | 0 |  
| Stack frame | Yes | No |  
| Saving of callee-saved registers | x19, x20, x29, x30 | None |  
| Memory accesses | 5 | 1 |  
The bodies of \`Core.Mix\` and \`Core.Idx\` are expanded into the caller, which removes two \`bl\` instructions and the stack and register save processing. Expressions spanning both functions are also optimized together. The 21.8% reduction in direct is the result of this change accumulating over 3,072 methods.

#### Why the improvement in iface is small

An interface call generated by IL2CPP has, in outline, the form {{list:interface_invoke_code}}.  
CODE START cpp | Outline of the interface call code generated by IL2CPP {{list:interface_invoke_code}}  
const VirtualInvokeData& invokeData \=  
    il2cpp\_codegen\_get\_interface\_invoke\_data(slot, obj, declaringInterface);  
return ((Func)invokeData.methodPtr)(obj, p1, p2, invokeData.method);  
CODE END  
The callee is a \`invokeData.methodPtr\` obtained at run time, so it cannot be resolved to a direct call like a normal C++ vtable call. However, the part where the method body calls a helper in another TU can be inlined, and iface also improved by 7.3%.

If interface / virtual calls are taking a long time, you can also consider \`sealed\`, receiving concrete types, and static dispatch via generics. What ThinLTO improves readily is the part that statically calls small functions in other TUs.

### 7.5 Optimization scope and improvement on real titles

In Title B, the improvement is concentrated on the main thread. While UnityMain decreased by \-3.21%, all non-UnityMain threads together changed by \+0.8%, which is within the 4% drift between sessions.

In the binaries as well, \`.so\` other than \`libil2cpp.so\` is almost unchanged. Two native plugins have identical md5, and the difference in \`.text\` of the remaining one is \+0.008%, within the range of build nondeterminism. The optimization by \`--compiler-flags\` this time did not reach these plugins.

UnityMain's \-3.2% is smaller than the benchmark's \-22%. On this screen, facial expressions, blinking, hair and clothing sway, IK, and so on run as jobs. These are contained in native binaries outside \`libil2cpp.so\` and are outside the scope of the optimization by this flag.

The improvement for IL2CPP generated code alone, excluding the out-of-scope processing, is considered larger than the \-3.21% of UnityMain as a whole. However, determining the exact value requires separating the in-scope and out-of-scope processing time with the Profiler. Jobs are also executed on the main thread by scheduling, so UnityMain's measurement also includes out-of-scope processing.

## 8\. Applying ThinLTO on iOS

I also applied ThinLTO to the iOS version of Title B. The effect was confirmed in the validation benchmark, but the real title did not gain an improvement that justified the increase in build time.

### 8.1 LTO structure on iOS

表: Comparison of the LTO structure on Android and iOS {{table:android_ios_lto_structure}}  
| Aspect | Android | iOS |  
|---|---|---|  
| il2cpp output | \`libil2cpp.so\` | \`libGameAssembly.a\` |  
| Final link | LLD called by il2cpp | ld64 when Xcode creates \`UnityFramework\` |  
| Arguments passed | \`--compiler-flags=-flto=thin \--linker-flags=-flto=thin\` | \`\--compiler-flags=-flto=thin\` only |  
| Where build time increases | Unity build step | \`Build ipa\` (xcodebuild) step |  

On iOS, il2cpp only creates an archive, so \`--linker-flags\` is not passed. LTO code generation happens at link time on the Xcode side, which reads the archive containing this bitcode.

Because il2cpp is responsible for compiling the generated code, the flag must be specified in \`AdditionalIl2CppArgs\`. Changing \`LLVM\_LTO = YES\_THIN\` in Xcode does not apply to the generated code.

Engine code is provided as a prebuilt \`libiPhone-lib.a\` and has no bitcode, so it is not subject to LTO. There was also no setting to swap in an LTO-applied engine, like the Android engine code LTO toggle (§3).

{{pagebreak}}

## 9\. Adopting it in your own title

On Android, we recommend first adding \`\-flto=thin\` to the Release configuration. In this benchmark, it gave CPU performance equivalent to Master with a smaller binary and a shorter build time. On the steady-state screen of a real title as well, total cycles decreased by 1.68% and UnityMain by 3.21% (§7.3).

We do not recommend the engine code LTO toggle (§3) in this configuration, because disabling Strip Engine Code causes a large increase in size and memory.

Manual ThinLTO on iOS did not provide an improvement commensurate with the increase in build time, so we decided not to adopt it.

Before adoption, examine the scripting time in the PlayerLoop with a Profiler capture of a Release build. The target of the manual flag is within \`libil2cpp.so\`; the render thread, GPU, engine internals, and GC are not targets. Jobs compiled by a separate AOT pipeline are also not included (§7.5). For titles that use DOTS/Jobs heavily, also check their processing time.

For example, if scripting takes 8 ms of a 33 ms frame, even a reduction of about 20% in that part shortens the whole frame by only about 1.6 ms. Consider adopting it only if scripting accounts for a large share of the whole frame and there is room for improvement, or if a high frame rate must be maintained.

If the increase in build time hampers daily development work, you can apply it only to builds from staging onward and not to everyday development builds. Because the flag is added in the build preprocessing ({{list:manual_thinlto_build}}), it can be switched for each type of build.

After configuring, confirm the application using the procedures in §3.1 and §5.2. The places to check are inputdata, the binary md5, \`-flto\` in the compile command, and the bitcode of object files. A build may succeed even when the LTO conditions are not met, so the build result alone cannot tell you whether it was applied.
